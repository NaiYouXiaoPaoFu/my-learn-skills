## Goals / Non-Goals

**Goals:**

- 建立“行为合约 -> 隐式满足 -> 接口值 -> 组合 -> 运行时检查”的接口主线。
- 通过 `io.Writer`、`fmt.Stringer`、`sort.Interface` 和 `http.Handler` 等标准库场景理解接口设计和可替换性。
- 重点纠正接口值的静态类型、动态类型、动态值与两类 `nil` 的区别。
- 让用户能判断方法集导致的实现关系，安全使用类型断言/类型开关，并能解释接口和泛型约束的边界。
- 每阶段以概念复述、编译判断、场景判断或最小排错题提供证据。

**Non-Goals:**

- 不重复完整讲解第 6 章方法、闭包或泛型；只在接口判断需要时回顾。
- 不展开反射、`unsafe`、运行时接口内部布局、性能基准和编译器实现。
- 不把所有标准库接口逐个背诵，不制作生产项目代码。
- 不在用户批准方案前开始正式教学或把未验证结论写成已掌握。

## Decisions

1. **按认知依赖而不是原章节顺序教学。** 先用方法集和 `io.Writer` 建立接口合约，再讲接口值与 `nil`，最后讲组合和类型检查。原因：历史记录表明方法集基础已有部分掌握，而 `nil`/断言是明确薄弱点；直接从整章顺序讲会掩盖薄弱边界。
   - 备选：严格按 7.1 至 7.14 逐节讲；不采用，因为会重复泛型/方法背景且 checkpoint 不聚焦。
2. **用标准库接口作主场景。** 以小接口和调用方需求解释抽象，优先 `io.Writer`/`fmt.Stringer`，再连接 `http.Handler`。原因：这些例子能直接展示“调用方只依赖行为，不依赖具体实现”。
   - 备选：只用自造 `Speaker` 示例；不采用，因为迁移到真实 Go API 的证据较弱。
3. **把接口值拆成静态类型、动态类型、动态值三层。** 对每个 `nil`/断言题都显式标注三者，避免只用“接口里装了对象”的模糊类比。
   - 备选：只讲接口是二元组；不采用，因为不利于解释携带 nil 指针和方法调用边界。
4. **checkpoint 采用短题逐阶段升级。** 阶段题验证局部概念，综合题同时覆盖方法集、隐式实现、nil、接口组合、断言和工程取舍。两轮不稳时回到更小概念，不继续堆题。
   - 备选：章节末一次性考试；不采用，因为无法及时定位是方法集还是接口值导致的错误。
5. **接口与泛型约束明确分轨。** 只复用用户已掌握的“泛型接口实例化 vs 具体实现值”结论，新增判断题对比运行时接口值与编译期类型约束，不重复泛型语法。
   - 备选：把泛型接口作为第 7 章主线；不采用，因为用户指定的是接口章节且已有独立泛型总结。

## Risks / Trade-offs

- [Risk] 接口值的抽象模型与实际运行结果不一致 → [Mitigation] 每个关键边界用最小 Go 片段或编译/输出预测验证。
- [Risk] 章节范围过大导致用户只记住术语 → [Mitigation] 每阶段只保留一个可验证目标，相关拓展登记为后续候选。
- [Risk] 中文译文与当前 Go 规范版本存在细节差异 → [Mitigation] 语言规则以 Go 官方规范为准，用户指定章节用于主线解释并标注链接。
- [Risk] 过早回写 level 造成错误长期状态 → [Mitigation] 只有通过综合 checkpoint 或用户明确确认才更新数据库。
