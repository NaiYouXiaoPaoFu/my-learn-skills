# 学习系统门禁

这份门禁约束所有学习型 skill：目标是通过真实项目理解工程知识，而不是生成泛泛课程。

## 核心原则

- 一个 skill 只做一类事，跨职责时交给下一个 skill。
- 一个学习切片只围绕一条业务链路、一个能力点或一个明确问题。
- 技术知识点要服务具体场景，例如接口读取、登录态、媒体上传、后台编辑、部署排错。
- 先理解问题边界，再讲实现；先讲为什么，再讲怎么做。
- 每轮教学都要有检验；没有检验，不视为完成。
- 稳定结论才回写文档，临时想法只留在当前对话或 issue。
- 用户粘贴 issue/PR 时，先把它当作精准上下文入口，不先扫全仓库。
- 教学前不默认用户掌握前置知识；讲过并通过检验后，才标记为掌握。
- 面试式追问要适可而止：默认 1 个主问题，最多 2 个追问，错了先补课。

## 拆解顺序

1. 业务场景：用户在项目里要完成什么。
2. 执行链路：请求、函数、数据或事件如何流动。
3. 设计边界：职责、协议、数据、权限、失败路径在哪里。
4. 知识点：本轮必须理解的最小概念是什么。
5. 验证方式：如何证明已经理解或实现正确。
6. 回写判断：这个结论是否会复用，是否需要沉淀。

## 教学与检验边界

- 先教，再检验；不能还没讲就把知识点当作已掌握。
- 用户答错时，先解释错因和正确思路，再判断是否追问。
- 连续两轮不稳时停止追问，记录卡点，回到更小概念。
- 学习笔记要记录场景、卡点、纠偏过程和掌握状态。

## Issue / PR 入口

- issue/PR 已提供目标、任务树和验收标准时，优先按它执行。
- 只加载与当前 issue/PR 直接相关的代码、测试、文档和知识点。
- 强粒度 issue 不需要重新拆分，只补必要知识和验证方式。
- 正常粒度 issue 可以补少量子任务、风险和知识点。
- 过粗 issue 先拆分；过碎 issue 先补业务场景。

## 工程判断问题

- 这个模块有几个变化原因？
- 入口、业务编排、持久化、DTO、横切逻辑是否混在一起？
- 如果失败，错误在哪一层被处理，用户看到什么？
- 这个设计为了当前阶段解决什么问题，又故意不解决什么？
- 如果并发、重试、重复提交、权限或网络失败出现，会发生什么？

## 不要做

- 不要把多个互不依赖的知识点塞进一个切片。
- 不要从名词列表开始教学。
- 不要为了“完整”讲超出当前问题太多的背景。
- 不要用高级架构名词代替边界分析。
- 不要没有验证口径就输出学习计划。
- 不要因为用户一次答错就连续追问多个类似问题。
