# 学习文档分层

用于 `learning-note-writer` 判断是否回写以及写到哪里。

## 分层

- `docs/design/`：长期有效的架构、边界、约束和选型理由。
- `docs/learning/`：概念解释、触发场景、用户卡点、误区、纠偏过程、检验结果、参考资料链接。
- `docs/decisions/`：重要设计决策，包含背景、选择、替代方案和后果。
- `openspec/` 或 issue：阶段任务、验证结果、未决点和临时 workaround。

## 是否值得回写

满足任一条件再考虑回写：

- 同一知识点、误区或卡点开始反复出现。
- 一个判断影响后续架构、教学或实现。
- 用户已经通过检验，结论稳定。
- 用户没有通过检验，但卡点清楚且后续需要复习。
- 阶段结束，需要让下一轮学习接得上。

## 学习笔记回写逻辑

- 记录“这次为什么讲”：issue、PR、代码链路、设计讨论或调试场景。
- 记录“哪里没懂”：用户说错、犹豫、混淆或无法迁移的点。
- 记录“怎么纠偏”：用哪个例子、对比、链路图或最小实操讲通。
- 记录“掌握到什么程度”：未教、讲过未检验、检验未通过、基本掌握、可迁移使用。
- 记录“参考了什么”：官方文档、框架文档、面经或项目资料链接，并放在对应知识点下。
- 记录“下次怎么接”：下次进入同类问题时先补哪个更小概念。

## 参考资料回写

- 如果教学时查了外部资料，学习笔记必须在对应知识点下保留链接。
- 官方文档、语言/框架文档、标准文档优先放在最前。
- 面经、博客、GitHub 仓库只能作为提问方式、案例或辅助理解来源。
- 不要把一份通用阅读清单代替本轮实际使用的资料链接。
- 如果本轮没有使用外部资料，写“参考资料：仅项目上下文”。

## 写法

- 先写结论，再写原因。
- 先写范围，再写细节。
- 先写稳定约定，再写可变内容。
- 学习笔记和设计决策不要混写。
- 不把“还没教过”写成“用户已掌握”。
- 不把外部链接堆到文末；要贴在对应知识点或卡点旁边。
- 每篇文档只解决一个主题。

## 不回写

- 一次性调试过程。
- 还没验证的猜测。
- 临时 workaround。
- 只是为了当前回答完整而补充的背景。
- 用户没有明显卡点，也没有稳定复用价值的普通问答。
